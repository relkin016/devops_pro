# @theory

## Как проходит собеседование DevOps

Типичные этапы:
1. **HR-скрининг** (15–30 мин): мотивация, ожидания, формат работы, зарплата.
2. **Технический скрининг** (30–60 мин): быстрые вопросы по базе — Linux, сети, Docker, K8s, CI/CD, IaC. Часто — по таблице вопросов от простого к сложному, пока не «упрётесь».
3. **Техническое интервью** (60–90 мин): глубокие вопросы по опыту, **траблшутинг-сценарии** («у вас 502, ваши действия»), иногда live-coding (Bash/Python), разбор манифестов/Dockerfile/Terraform.
4. **System design / архитектура** (middle+): спроектировать CI/CD, отказоустойчивую инфраструктуру, логирование, миграцию в K8s.
5. **Практическое задание** (иногда): поднять сервис в Docker/K8s, написать Terraform-модуль, Ansible-роль, пайплайн.
6. **Финал с руководителем/командой**: поведенческие вопросы, культура, ценности.

### Что реально оценивают
- **Понимание «как это работает внутри»**, а не заученные команды.
- **Системность** в траблшутинге: гипотеза → проверка → вывод.
- **Опыт**: конкретные задачи, которые вы решали, масштаб, ваши решения и их последствия.
- **Мышление о надёжности и безопасности**: «а что будет, если это упадёт?», «где тут секреты?».
- **Коммуникация**: умение объяснить, задать уточняющие вопросы, признать, что чего-то не знаете.

> [!tip] Если не знаете ответ
> Не выдумывайте. Скажите: «С этим напрямую не сталкивался, но рассуждал бы так…» — и порассуждайте от базовых принципов. Это ценится выше, чем уверенная ошибка.

## Как отвечать: структура и STAR

### Технический ответ
1. **Определение** в одном предложении.
2. **Как работает** (механизм).
3. **Зачем/когда применять** и альтернативы.
4. **Пример из практики** или подводный камень.

Пример: «Readiness probe — проверка готовности пода принимать трафик (1). kubelet выполняет её периодически, при провале под убирается из endpoints сервиса, но не перезапускается (2). Нужна, чтобы не слать трафик в прогревающееся или перегруженное приложение; liveness — для зависаний (3). У нас была авария, когда в liveness проверяли БД — при её сбое перезапустились все поды; вынесли проверку зависимостей в readiness (4)».

### Поведенческие вопросы — STAR
- **S**ituation — контекст.
- **T**ask — ваша задача.
- **A**ction — что **вы** сделали (не «мы»).
- **R**esult — измеримый результат и выводы.

Подготовьте 5–7 историй: сложный инцидент, автоматизация, сэкономившая время/деньги, миграция, конфликт/разногласие, ошибка и что вы из неё вынесли, задача, где пришлось быстро разобраться в новом.

### Частые «нетехнические» вопросы
- Расскажите о себе (2 минуты: опыт → ключевые технологии → лучшие достижения → почему эта позиция).
- Самый сложный инцидент в вашей практике.
- Что вы автоматизировали и какой эффект?
- Как вы относитесь к дежурствам?
- Как вы учитесь новому?
- Как поступите, если разработчики требуют срочно задеплоить в обход процесса?
- Почему уходите с текущего места?

## System design для DevOps

### Подход (одинаков для любой задачи)
1. **Уточнить требования**: функциональные (что делает) и нефункциональные — нагрузка (RPS, данные), доступность (SLO), латентность, RTO/RPO, безопасность и комплаенс, бюджет, размер команды, облако/он-прем.
2. **Высокоуровневая схема**: пользователи → DNS/CDN → балансировщик → приложения → данные; CI/CD; наблюдаемость.
3. **Детализация** ключевых компонентов и **обоснование выбора** (почему K8s, а не ECS; почему PostgreSQL + реплики).
4. **Отказы**: что будет при падении каждого компонента, зоны, региона.
5. **Масштабирование**, **безопасность**, **стоимость**, **эксплуатация** (мониторинг, алерты, бэкапы, обновления).
6. Компромиссы и что сделать в первую очередь (MVP), а что — потом.

### Задача: отказоустойчивое веб-приложение
```text
Route 53 (health checks) → CloudFront (+WAF) → ALB (3 AZ)
  → EKS: Deployment (≥3 реплик, anti-affinity по зонам, HPA, PDB) ← Karpenter/CA
      → ElastiCache Redis (репликация, multi-AZ)
      → RDS PostgreSQL Multi-AZ (+ read replica) ← PgBouncer
      → S3 (статика, загрузки) + SQS для фоновых задач → воркеры
CI/CD: GitHub Actions (тесты, сборка, Trivy, cosign) → ECR → Argo CD (GitOps) → Argo Rollouts (canary)
Наблюдаемость: Prometheus + Grafana + Alertmanager, Loki, Tempo/OTel, SLO burn-rate алерты
Безопасность: IRSA, Secrets Manager + ESO, NetworkPolicy, Pod Security restricted, private subnets, VPC endpoints
IaC: Terraform (сеть, EKS, RDS) в слоях с remote state; DR: бэкапы RDS + снапшоты в другом регионе
```

### Задача: CI/CD для 50 микросервисов
Ключевые моменты: шаблоны пайплайнов (GitLab CI components / reusable workflows / Jenkins shared library), единые стандарты сборки (Dockerfile-шаблоны, базовые образы), монорепо vs полирепо, кэширование и параллелизм, артефакты в общем реестре, неизменяемые теги, сканирование и подпись, GitOps-репозиторий с окружениями, прогрессивная доставка, автоматическое обновление зависимостей (Renovate), метрики DORA, self-service для команд.

### Задача: централизованное логирование
Агенты на нодах (Fluent Bit/Vector/OTel Collector) → буфер (Kafka при больших объёмах) → хранилище (Loki — дёшево, по labels; OpenSearch — полнотекст; ClickHouse — аналитика) → Grafana/Kibana. Вопросы: объём в день и ретенция, структурированные логи, парсинг, маскирование PII, мультиарендность и доступ, стоимость хранения (горячее/холодное в S3), алерты по логам, обратное давление при отказе хранилища.

### Задача: миграция монолита с ВМ в Kubernetes
Оценка (stateful-части, конфиги, сессии, файлы на диске, cron), контейнеризация (12-factor: конфиг из env, логи в stdout, stateless, graceful shutdown), вынос состояния (сессии в Redis, файлы в S3, БД — managed), manifests/Helm, CI/CD, наблюдаемость, параллельный запуск и постепенное переключение трафика (взвешенный DNS/балансировщик), план отката, затем — при необходимости — дробление на сервисы (strangler fig).

### Задача: деплой без простоя
Rolling/canary/blue-green, readiness probes, graceful shutdown (SIGTERM, preStop, connection draining), обратно совместимые миграции (expand/contract), PDB, достаточный запас мощности, автоматический откат по метрикам, feature flags.

## Live-coding: Bash и Python

Типичные задачи на собеседовании — небольшие скрипты эксплуатации. Важно: обработка ошибок, читаемость, крайние случаи, проговаривание решения вслух.

### Топ IP из access-лога
```bash
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
```

```python top_ips.py
import sys
from collections import Counter

def top_ips(path: str, n: int = 10) -> list[tuple[str, int]]:
    counter = Counter()
    with open(path, encoding="utf-8", errors="replace") as f:
        for line in f:
            ip = line.split(" ", 1)[0]
            if ip:
                counter[ip] += 1
    return counter.most_common(n)

if __name__ == "__main__":
    for ip, count in top_ips(sys.argv[1]):
        print(f"{count:>8} {ip}")
```

### Проверка доступности списка URL с таймаутом
```bash check_urls.sh
#!/usr/bin/env bash
set -euo pipefail
fail=0
while IFS= read -r url; do
  [[ -z $url || $url == \#* ]] && continue
  code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 "$url" || echo "000")
  if [[ $code =~ ^(2|3) ]]; then
    echo "OK   $code $url"
  else
    echo "FAIL $code $url" >&2
    fail=1
  fi
done < "${1:?usage: $0 urls.txt}"
exit $fail
```

```python check_urls.py
import concurrent.futures as cf
import sys
import urllib.request

def check(url: str, timeout: float = 5.0) -> tuple[str, int | str]:
    try:
        with urllib.request.urlopen(url, timeout=timeout) as resp:
            return url, resp.status
    except Exception as exc:  # noqa: BLE001 — отчёт об ошибке любого типа
        return url, type(exc).__name__

urls = [u.strip() for u in open(sys.argv[1]) if u.strip() and not u.startswith("#")]
with cf.ThreadPoolExecutor(max_workers=20) as pool:
    for url, status in pool.map(check, urls):
        print(f"{status}\t{url}")
```

## Сквозной сценарий: «Сайт не открывается»

Самый частый вопрос. Отвечайте «по пути запроса», называя команды на каждом шаге:

1. **Уточнить**: у всех или у части? Какая ошибка (таймаут, DNS, 5xx, сертификат)? С какого времени? Были ли изменения?
2. **DNS**: `dig site.com` — резолвится ли, на правильный ли IP, не истёк ли домен, не сломали ли записи.
3. **Сеть до входа**: `curl -v`, `mtr`, порт 443 открыт? CDN/WAF не блокирует? Security groups/файрвол?
4. **TLS**: `openssl s_client` — сертификат не истёк, цепочка полная, имя совпадает.
5. **Балансировщик/Ingress**: health checks, есть ли живые бэкенды, логи (502/503/504?).
6. **Приложение**: поды/процессы живы? `kubectl get pods`, рестарты, логи, readiness; на ВМ — `systemctl status`, `journalctl`.
7. **Ресурсы**: CPU, память (OOM), диск (заполнен?), дескрипторы, соединения.
8. **Зависимости**: БД (соединения, блокировки, лаг), кэш, очереди, внешние API.
9. **Изменения**: последний деплой/конфиг/миграция → откат как первое средство восстановления.
10. **После**: коммуникация, postmortem, алерт, который поймал бы раньше.

| Контейнеры | Dockerfile, compose, базовые команды | оптимизация образов, безопасность, сети, рантаймы | платформа сборки, supply chain security |
| Kubernetes | основные объекты, kubectl, деплой приложения | Helm, probes, ресурсы, RBAC, Ingress, траблшутинг | архитектура кластеров, multi-tenancy, апгрейды, операторы, сети CNI |

| CI/CD | настроить пайплайн по образцу | проектировать пайплайны, стратегии деплоя, секреты | платформа доставки, GitOps для многих команд, DORA |
| Наблюдаемость | дашборды, читать алерты | PromQL, алерты, логи, трейсинг | SLO, стратегия observability, масштабирование стека |

# @interview

## [junior] Что такое DevOps своими словами?
Культура и набор практик, объединяющих разработку и эксплуатацию для быстрой и надёжной поставки ценности: общая ответственность за продукт в проде, автоматизация (CI/CD, IaC), быстрые циклы обратной связи (мониторинг, метрики), маленькие частые изменения, обучение на ошибках. DevOps — не должность и не набор инструментов, хотя часто так называют роль инженера платформы/инфраструктуры.

## [junior] Что такое 12-factor app?
Методология облачных приложений: один кодбейс, явные зависимости, конфигурация в окружении, внешние сервисы как подключаемые ресурсы, разделение build/release/run, stateless-процессы, привязка к порту, масштабирование процессами, быстрый старт и graceful shutdown, паритет окружений, логи как поток событий в stdout, административные задачи как разовые процессы. Это основа «контейнеро-пригодности» приложения.

## [middle] Пользователи жалуются, что сайт медленный. Ваши действия?
Уточнить масштаб (все/регион/конкретные страницы), посмотреть метрики RED (латентность p95/p99, ошибки, RPS) и сравнить с нормой, проверить последние изменения. Разложить время запроса: DNS/TCP/TLS/TTFB (`curl -w`), трейсинг — где теряется время (приложение, БД, внешний API). Проверить saturation (CPU throttling, память, пулы соединений, очереди), БД (медленные запросы, блокировки, лаг реплик), кэш (hit ratio), сеть. Mitigation (масштабирование, откат, отключение тяжёлой функции), затем root cause.

## [middle] Как бы вы организовали деплой нового микросервиса с нуля?
Репозиторий с кодом и Dockerfile (multi-stage, non-root), CI: линт, тесты, сборка, сканирование, push с тегом SHA; Helm-чарт/Kustomize с probes, ресурсами, PDB, HPA; секреты через ESO/Vault; GitOps-репозиторий с окружениями; Argo CD; мониторинг (метрики RED, ServiceMonitor, дашборд, алерты по SLO), логи в stdout в JSON, трейсинг OTel; документация и runbook.

## [middle] Расскажите о самом сложном инциденте в вашей практике.
Ответ по STAR: контекст и влияние, как обнаружили, ваши действия по восстановлению и диагностике, первопричина, что изменили после (алерты, автоматизация, архитектура). Важно показать системность, спокойствие и выводы, а не героизм.

## [middle] Как вы обеспечиваете, что инфраструктура воспроизводима?
Всё как код в Git: Terraform для ресурсов, Ansible/Packer для образов и конфигурации, Helm/Kustomize + GitOps для Kubernetes, пайплайны как код. Закреплённые версии (провайдеры, модули, образы, зависимости), запрет ручных изменений (или drift detection), окружения из одного кода с разными параметрами, регулярное пересоздание (эфемерные окружения), документация в README рядом с кодом.

## [senior] Как бы вы перевели компанию с ручного деплоя на CI/CD?
Начать с аудита текущего процесса и боли, выбрать пилотный сервис, быстро показать ценность (автоматическая сборка и тесты, деплой в staging по кнопке), стандартизировать (шаблоны пайплайнов, контейнеризация, IaC), постепенно масштабировать на другие команды, обучать и документировать, внедрять метрики DORA для демонстрации эффекта, двигаться к частым маленьким релизам и прогрессивной доставке. Важна работа с людьми, а не только инструменты.

## [middle] Как вы относитесь к ручным изменениям в проде?
Только в экстренных ситуациях для восстановления сервиса, с фиксацией в канале инцидента, и обязательно затем отразить изменение в коде (IaC/GitOps) или откатить — иначе дрейф и сюрпризы при следующем apply. В штатном режиме — только через код, ревью и пайплайн; доступ на запись в прод — минимальный и через break-glass процедуру.

## [junior] Какие языки программирования нужны DevOps-инженеру?
Bash — обязательно для автоматизации и работы в Linux. Python или Go — для более сложной автоматизации, работы с API облаков, своих инструментов и операторов. Плюс декларативные языки: YAML, HCL, Jinja2/Go templates, PromQL. Умение читать код приложений на языке команды очень помогает в траблшутинге.

## [senior] Как вы бы оценили и уменьшили стоимость инфраструктуры в 2 раза?
Сначала видимость: теги, разбивка по командам/сервисам, Cost Explorer/Kubecost. Затем быстрые победы: удалить неиспользуемое, выключать неработающие окружения, rightsizing по реальной утилизации, gp3, lifecycle хранилищ, сетевые расходы (NAT, межзональный трафик). Затем средние: Savings Plans/RI на базу, Spot для stateless/CI, Graviton, плотность в K8s (requests по факту, bin packing, Karpenter consolidation). Затем архитектурные: кэширование, serverless для нерегулярной нагрузки, пересмотр ретенции логов/метрик. Встроить FinOps-процесс: бюджеты, алерты, ответственность команд.

## [middle] Что такое Infrastructure as Code и какие у него преимущества?
Управление инфраструктурой через машиночитаемые определения в системе контроля версий. Преимущества: воспроизводимость, ревью и история изменений, автоматизация и скорость, документация как код, тестирование, меньше человеческих ошибок, лёгкое создание идентичных окружений и восстановление после аварий.

# @troubleshooting

## [high] Сценарий: после деплоя выросла доля 5xx
**Ход мысли для собеседования:**
1. Корреляция по времени с деплоем → **сначала откат** (`helm rollback`, `kubectl rollout undo`, revert в GitOps) — восстанавливаем сервис.
2. Подтвердить, что после отката ошибки ушли.
3. Расследование: логи новой версии (стектрейсы), различия конфигурации (новые env, секреты, флаги), миграции БД (совместимость!), зависимости (новая версия библиотеки, другой эндпоинт), ресурсы (новая версия потребляет больше памяти → OOM).
4. Почему не поймали раньше: тесты, staging не похож на прод, нет canary с автоматическим анализом.
5. Action items: canary + анализ метрик, smoke-тесты после деплоя, алерт на error rate.

## [high] Сценарий: закончилось место на диске сервера БД ночью
**Ход мысли:**
1. Влияние: БД перестала принимать запись → приложение отдаёт ошибки.
2. Быстро освободить место **безопасно**: логи БД/ОС, старые бэкапы на том же диске, `journalctl --vacuum`; **не трогать** файлы данных и WAL вручную.
3. Расширить том (облако: увеличить EBS → `growpart` → `resize2fs`/`xfs_growfs` онлайн).
4. Найти причину роста: WAL (слот репликации, архивация), bloat, логи, временные файлы запросов.
5. Профилактика: алерт на 80% и `predict_linear`, ретенция, отдельные тома для данных/WAL/логов.

## [medium] Сценарий: «у меня локально работает, а в Kubernetes — нет»
**Чеклист:** приложение слушает `0.0.0.0`, а не `localhost`; переменные окружения и секреты присутствуют в поде; конфиги и пути (read-only rootfs, отсутствие записи в каталог); пользователь (non-root не может писать в каталоги образа, порты < 1024); архитектура образа (arm64 на маке vs amd64 в кластере); DNS-имена зависимостей (имена сервисов, namespace); NetworkPolicy; ресурсы (OOM при лимите); readiness/liveness пути и порты; часовой пояс и локаль; проверка через `kubectl debug`/`port-forward`.

# @quiz

? Что делать первым, если после деплоя резко выросли ошибки?
- Искать баг в коде
- Перезапустить все поды
+ Откатить деплой и восстановить сервис
- Масштабировать БД
> Mitigation прежде root cause.

? Какой принцип 12-factor про логи?
- Писать в файлы в /var/log
+ Писать поток событий в stdout, сбор и хранение — задача окружения
- Хранить логи в БД приложения
- Отключать логи в проде
> Это упрощает сбор логов в контейнерах.

? Метод STAR используется для:
+ Структурирования ответов на поведенческие вопросы
- Оценки задач в спринте
- Планирования мощностей
- Расчёта SLO
> Situation, Task, Action, Result.

? С чего начать system design задачу на собеседовании?
- С выбора облака
- С рисования Kubernetes
+ С уточнения функциональных и нефункциональных требований
- С оценки стоимости
> Без требований невозможно обосновать решения.

? Приложение в поде недоступно через Service, но работает при `kubectl exec ... curl localhost:8080`. Наиболее вероятно:
+ Приложение слушает 127.0.0.1 вместо 0.0.0.0, или не тот targetPort
- Сломан CoreDNS
- Нода NotReady
- Нет PVC
> Через localhost внутри пода доступно, а по IP пода — нет.
